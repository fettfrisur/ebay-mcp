# eBay MCP connector: handoff for the next Claude

Written 2026-10-24 at the end of the session that built this. Read this before touching the Worker.

## What exists

A custom MCP server that gives Claude live eBay.de search with seller reputation. The user built it with Claude in one long chat; Claude is its only user, so output is designed for Claude to read.

- **Runtime:** Cloudflare Worker `ebay-mcp`, account identity omitted, single module file, no dependencies, compatibility_date 2025-09-01
- **Endpoint:** `https://<your-worker>.workers.dev/mcp` (Streamable HTTP, hand-rolled JSON-RPC: initialize, ping, tools/list, tools/call)
- **Added in Claude** as a custom connector named "eBay MCP", auth "No sign-in" plus request header `x-api-key`
- **Current version:** 2.0.1. Source of truth is the deployed script; the user also has `ebay-mcp-worker.js`

## Secrets (names only; values never go in chat)

| Worker secret | Contents |
|---|---|
| `EBAY_CLIENT_ID` | eBay production App ID (contains `-PRD-`) |
| `EBAY_CLIENT_SECRET` | eBay production Cert ID (starts `PRD-`). Not the Dev ID, which looks like a UUID; that mix-up happened once |
| `ACCESS_KEY` | random string the user set; Claude sends it as `x-api-key` |

All three must stay type **secret_text**. Plain-text vars get wiped on API redeploys and are readable in the dashboard.

## Security model

1. **IP allowlist:** only `cf-connecting-ip` in Anthropic's MCP egress range `160.79.104.0/21` gets in (else 403). Side effect: Claude's own sandbox (Google Cloud) cannot call the Worker; test through the connector instead. Env var `ALLOW_ALL_IPS="true"` disables the check for testing.
2. **Key:** only accepted as `x-api-key` or `Authorization: Bearer` on path `/mcp` (else 404). The old key-in-URL path was removed on purpose.
3. **eBay side:** app-only OAuth (client_credentials), no eBay user login. eBay Marketplace Account Deletion exemption granted on the basis of "I do not persist eBay data", so **never add caching or logging of eBay results**. Only OAuth tokens live in isolate memory.

## Tools (all annotated read-only, so no per-call approval)

- **`search_ebay`**: Browse API item_summary/search on EBAY_DE, items located in DE. Params: query, min/max_price, condition (any, new, used=conditionId 3000 i.e. working only, refurbished, for_parts=7000), buy_it_now_only, postal_code (default 70173 Stuttgart), radius_km (local-pickup filter), sort, category_id (9355 = Handys & Smartphones; use it, otherwise cases and spare parts flood results), limit ≤ 50. Inlines reputation for up to 20 distinct sellers (2 Feedback API calls each, to stay under the free plan's 50 subrequests).
- **`get_ebay_item`**: item details plus condition note, returns, shipping, specs (localizedAspects), description, up to 5 photos, reputation.
- **`get_seller_feedback`**: deep dive into feedback received as seller: 30/180/365-day counts plus comments with item title, price, replies. Filters: comment_type (default negative), period_days, topic (eBay AI topics like condition, description, shipping), sort, limit 25–200, offset.

## Output format (agreed with the user)

Plain text, not JSON: short labels, no cryptic symbols, one block per listing. The user explicitly asked that every "unavailable" carry a reason in parentheses, e.g. `seller rep: unavailable (eBay Feedback API quota exceeded)`. Keep it that way.

## eBay API facts learned the hard way

- Feedback API (`/commerce/feedback/v1`, beta) works with client_credentials and scope `https://api.ebay.com/oauth/api_scope/commerce.feedback.readonly`. This keyset has it.
- `feedback_rating_summary` returns 7/30/180/365-day rows, **no lifetime**. Rows come combined, `userRoleType: BUYER` and `userRoleType: SELLER`. **Use the SELLER row**; it reproduces eBay's displayed % exactly.
- In `GET /feedback`, the `role` filter means **the rated user's role**, despite docs suggesting the rater. `role:SELLER` means feedback received as seller. `role:BUYER` hid a real negative.
- `commentType` takes one value only (`NEGATIVE|NEUTRAL` gives a 400).
- Lifetime negatives: `GET /feedback?...filter=role:SELLER,commentType:NEGATIVE&sort=TIME` and read `pagination.total`.
- DSR (detailed star ratings) summaries come back empty even for a 17k-rating shop, so they're not offered.
- Browse `seller.feedbackPercentage` covers only the last 12 months; "0.0%" with a high score usually means no recent ratings, not a bad seller.
- `sellerAccountType` BUSINESS vs INDIVIDUAL matters in Germany (statutory returns only from business sellers).

## How to deploy (via the Cloudflare Code API connector)

The user's "Cloudflare Code API" connector (`mcp.cloudflare.com`) can do everything; the older "Cloudflare Developer Platform" one cannot deploy.

1. Edit and test locally in the sandbox (`node --check`; import the module and call `fetch()` with mocked `globalThis.fetch`).
2. `sha256sum` the file, then `gzip -9 | base64 -w0` (keeps the paste short).
3. In `execute`: decode, gunzip with `DecompressionStream`, **verify the SHA-256 before uploading**, then `PUT /accounts/{id}/workers/scripts/ebay-mcp` as multipart with metadata `{ main_module: "worker.js", compatibility_date: "2025-09-01", keep_bindings: ["secret_text", "plain_text"] }`.
4. Check the bindings afterwards (all three secrets still `secret_text`).
5. Test through the eBay connector tools. Note: a chat only sees the tool list from when it started, so new tools need a new chat.

**Exploring unknown eBay responses:** because of the IP lock, add a temporary debug passthrough (e.g. `get_ebay_item` with `item_id: "debug:<read-only eBay path>"`, regex-limited to `/commerce/feedback/v1/` and `/buy/browse/v1/`), deploy, look, then **remove it** in the next deploy.
